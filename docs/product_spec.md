# CMMS 제품 사양서

## 1. 문서 목적

이 문서는 CMMS의 업무 정책과 사용자 관점의 기능을 정의하는 제품 정본이다. API·Entity·DB·화면 구현 규칙은 `docs/tech_spec.md`, 공통 코드 작성 규칙은 `docs/coding_conventions.md`를 따른다.

CMMS는 회사·사업장·부서·창고를 기준으로 설비, 예방점검, 작업, 작업허가, 자재·재고, 구매, 결재, 게시판을 관리한다.

| 코드 | 모듈 |
|---|---|
| MDM | 회사·사업장·부서·사용자·창고·공통코드·Role·Role 권한 |
| EQP | 설비·점검주기 |
| INV | 자재 마스터 |
| STK | 재고·입출고·이동·조정·마감 |
| PUR | 구매요청 |
| POR | 구매오더·구매관리 |
| PM | 예방점검 |
| WO | 작업지시 |
| WP | 작업허가 |
| APR | 전자결재 |
| BRD | 게시판·댓글 |

## 2. 조직과 접근범위

### 2.1 회사·사업장·부서

- 회사는 업무 데이터와 권한을 격리하는 최상위 단위다.
- 사업장은 설비와 현장업무가 발생하는 장소다. 모든 회사에는 본사 사업장이 있다.
- 부서는 사용자의 소속과 기본 Role·Scope를 관리한다.
- `homePlantId`는 사용자의 기본 사업장이고 `activePlantId`는 현재 화면의 조회 사업장이다.
- 회사 범위 사용자는 전체 또는 특정 사업장을 선택한다.
- 사업장 범위 사용자는 `homePlantId` 사업장만 선택·조회한다.
- 회사 범위의 초기 조회값은 전체, 사업장 범위의 초기 조회값은 `homePlantId`다.

### 2.2 창고

- 창고는 회사 내에서 고유한 재고 보관 단위다.
- `plantId`가 있는 창고는 해당 사업장 창고다.
- `plantId`가 없는 창고는 회사 공통 중앙창고다.
- 회사 범위 사용자는 허용된 전체 창고에 접근할 수 있다.
- 사업장 범위 사용자는 해당 사업장 창고에 접근한다.
- 회사 공통 창고는 특정 사업장에 귀속되지 않으며 구매 입고와 일반 창고 이동의 선택 대상이 될 수 있다.

### 2.3 사용자와 권한

| 구분 | 정책 |
|---|---|
| SYSTEM | 회사 업무가 아닌 시스템 관리만 수행하며 `SystemShell`을 사용한다. |
| ADMIN | 회사 생성 시 전체 모듈 CRUD를 기본 부여받으며 회사 격리·사업장 범위·상태·결재·재고 검증은 동일하게 적용한다. |
| 일반 사용자 | 부서 모듈 권한과 조직 범위에 따라 접근한다. |

모듈 권한은 다음 CRUD 액션을 개별 관리한다.

- `C`: 생성
- `R`: 목록·상세 조회
- `U`: 수정
- `D`: 삭제

결재 승인·반려는 모듈 권한이 아니라 결재선과 현재 결재단계로 판단한다. 메뉴는 업무 모듈 권한만으로 제거하지 않으며 화면 버튼과 API에서 권한을 검사한다.

## 3. 공통 업무정책

### 3.1 문서와 상태

문서형 업무는 CRUD와 상태 전이를 구분한다.

| 코드 | 의미 |
|---|---|
| T | 임시저장 |
| P | 결재중 |
| C | 결재완료·확정 |
| S | 직접확정 |
| R | 반려 |
| X | 취소 |
| E | 종료 |

- 본인의 임시저장 문서는 해당 모듈의 U/D 권한과 본인 여부를 모두 확인한 뒤 수정·삭제할 수 있다.
- 결재중·확정 문서는 직접 수정하지 않는다.
- 확정된 재고거래는 삭제하지 않고 반대 거래로 취소한다.
- 결재 이력과 재고 이력은 보존한다.

### 3.2 감사·삭제·번호

- 독립 문서는 생성일시·생성자·수정일시·수정자를 보존한다.
- 업무 데이터 삭제는 논리삭제를 기본으로 한다.
- 재고·결재·로그인 이력은 append-only 성격으로 보존한다.
- 업무번호는 회사·모듈·부서·년월·일련번호 체계를 사용한다.
- 출력물에는 회사, 출력일시, 출력자를 표시한다.

### 3.3 숫자·단위

- BE와 DB는 수량·금액을 Decimal 및 numeric으로 처리한다.
- BE/DB 계산과 저장은 소수점 4자리를 유지한다.
- FE 수량·측정값은 소수점 2자리로 표시한다.
- FE 금액은 정수로 반올림해 표시한다.

### 3.4 첨부파일·게시판

- 첨부파일은 원문서의 회사·조회 권한을 상속한다.
- 게시판은 전자결재와 연계하지 않는다.
- 댓글이 있는 게시글은 작성자도 삭제할 수 없다.
- 작성자는 본인의 게시글과 댓글을 수정할 수 있다.

## 4. 기준정보·마스터

### 4.1 기준정보

MDM은 회사, 사업장, 부서, 사용자, 창고, 공통코드, Role과 Role별 모듈 CRUD 권한을 관리한다. 참조 조회는 인증된 회사 범위와 필요한 필드만 반환한다.

### 4.2 설비

설비는 사업장에 소속하며 설비코드, 명칭, 위치, 유형, 설치일, 제조사, 규격, 모델, 일련번호와 점검주기를 관리한다. 업무 이력이 있는 설비는 물리삭제하지 않는다.

PM 실적이 결재 완료되면 `PmRecord.workDate`를 기준으로 해당 설비의 `checkTypeCode`와 일치하는 점검주기의 최근 점검일과 다음 점검일을 갱신한다.

### 4.3 자재

자재는 회사 공통 마스터다. 코드, 명칭, 유형, 단위, 제조사, 규격, 모델, 일련번호, 안전재고, 재주문점, 리드타임, 비고를 관리한다.

- 자재 마스터에는 창고별 조직 소유 필드를 두지 않는다.
- 신규 자재 생성 시 회사 내 기존 창고마다 재고 상태를 0수량·0금액으로 생성한다.
- 신규 창고 생성 시 회사의 모든 자재마다 재고 상태를 0수량·0금액으로 생성한다.

## 5. 예방점검·작업·허가

### 5.1 PM

설비 마스터는 `pmTargetYn`으로 PM 대상 여부를 관리하고, 점검유형별 주기·마지막 점검일·다음 점검일을 저장한다. PM Record는 실적 전용 문서이며 `stage` 값을 저장하지 않는다. PM 화면은 실적 목록과 신규 실적 입력만 제공한다. 사용자는 설비 마스터의 점검유형을 확인하고 실적을 직접 입력한다. 다음 점검일 이전 입력도 허용하며, 템플릿은 `설비 + 점검유형` 기준의 선택형 편의기능이다. 기존 PM 계획 문서와 결재이력은 보존하되 정기 PM의 기본 화면에서는 사용하지 않는다.

### 5.2 WO

작업지시는 사업장·설비·관리부서·작업내용·담당자·예정일·실적·소요시간·비용·상태를 관리한다. 확정·진행·완료는 상태 전이로 처리한다.

### 5.3 WP

작업허가는 작업·설비의 위험·안전·승인·유효기간을 관리한다. 승인 전에는 허가 완료로 처리하지 않으며, 만료·취소된 허가는 유효 허가로 사용하지 않는다.

## 6. 전자결재

- 업무문서는 `approvalId`로 결재문서를 연결한다.
- 결재문서는 원 업무 모듈과 원 문서번호를 보유한다.
- 상신자는 결재선의 시작 단계로 기록한다.
- 승인·반려는 현재 결재자와 결재순서를 검증한다.
- 반려 시 기존 결재 이력을 보존한다.
- 결재 결과에 따라 원 업무문서 상태를 갱신한다.

## 7. 구매·재고 업무

### 7.1 구매요청(PR)

PR 한 건은 하나의 요청창고를 가진다. header에 요청자·부서·사업장·요청창고·요청일·제목·상태를 두고, item에 자재·요청수량·단위를 둔다. PR 수령수량을 별도 저장하거나 창고 이동과 연계하지 않는다.

```text
임시저장 → 결재상신 → 결재완료 → 발주 → PO 입고 → 종료
```

### 7.2 구매오더(PO)

- 여러 PR을 하나의 PO로 통합할 수 있다.
- 하나의 PR을 여러 PO로 분할할 수 있다.
- 결재연계 전인 PO는 C 권한으로 임시저장(T)하고 A 권한으로 직접확정(S)한다.
- 신규 PO 임시저장은 C 권한, 본인이 생성한 기존 T 문서의 수정 임시저장은 U 권한을 사용한다.
- 독립 PO는 T 상태에서 헤더와 품목을 함께 수정한다. PR 배부 기반 PO는 헤더와 allocation을 수정하며 품목을 직접 교체하지 않는다.
- PO item은 자재별 합산 발주수량을 관리한다. 입고수량과 잔량은 STK 재고전표 참조로 계산한다.
- PO와 PR item의 수량 관계는 PO allocation으로 보존한다.
- 여러 요청창고가 포함된 PO는 PR allocation으로 목적 창고를 결정한다.

### 7.3 PO allocation

- PO item별 allocation 합계는 PO 발주수량과 일치한다.
- PR item별 전체 PO allocation 합계는 요청수량을 초과하지 않는다.
- 같은 PR item을 여러 PO에 분할 배부할 수 있다.
- allocation에는 완료수량을 저장하지 않는다.

PO는 신규·수정 시 T 상태로 먼저 저장·검증한 뒤 자체확정한다. 자체확정 action에서는 T 상태를 S 상태로 변경하며, 저장 단계의 품목·Allocation 검증을 반복하지 않는다.

### 7.4 입고

입고 잔량은 PO 발주수량에서 `refModule=POR`로 연결된 STK 입고전표 수량을 뺀 값이다.

- 부분입고를 허용한다.
- 입고수량은 PO item 잔량을 초과할 수 없다.
- 입고는 STK 수불관리에서 구매오더를 선택해 일반 입고 전표로 생성한다.
- 입고 전표는 PO 번호와 PO item 번호를 참조하고, PO item 잔량을 초과할 수 없다.
- 입고 창고는 사용자가 접근 가능한 창고 중 선택한다. PO 입고가 PR 수령수량이나 allocation을 변경하지 않는다.

### 7.5 창고이동

창고 이동은 출발창고·도착창고·자재·수량을 입력하고 재고만 변경한다. PUR·POR·allocation과 연계하지 않는다. 사용자가 plant를 선택하면 해당 범위의 창고만 검색되며, 이동 자체는 plant 간 거래가 아니라 warehouse-to-warehouse 거래다.

이동 전표는 하나의 전표 안에 출발창고 OUT item과 도착창고 IN item을 함께 가진다.

### 7.6 조정·취소

- 재고조정은 기존 재고 유형과 사유 상수를 사용한다.
- 조정 후 재고가 음수가 될 수 없다.
- 확정 입고·출고 취소는 반대 유형의 신규 거래를 생성한다.
- 후속 거래가 있는 재고거래는 직접 취소하지 않는다.

### 7.7 재고·마감

- 재고 상태는 회사·창고·자재별 현재고·현재금액이다.
- 재고 전표는 업무 처리 단위다.
- 재고 이력은 실제 증감 원장이다.
- 입고는 양수, 출고는 음수로 원장에 기록한다.
- 이동은 출발창고 음수, 도착창고 양수로 기록한다.
- 월마감은 기초재고와 당월 입고·출고·이동·조정을 집계한다.
- 마감된 월에는 재고거래를 생성할 수 없다.

## 8. 화면·사용성

- 일반 사용자는 AppShell, SYSTEM 사용자는 SystemShell을 사용한다.
- 권한이 없는 등록·수정·상태변경 버튼은 비활성화하거나 표시하지 않는다.
- 목록·상세·저장·상태변경은 로딩·성공·실패·빈 상태를 표시한다.
- 구매요청과 구매오더는 별도 목록·상세 흐름으로 제공한다.
- 재고처리 화면은 구매오더 입고, 일반 입고·출고·창고이동·조정·취소·마감을 제공한다.
