# CMMS-NODE 제품 사양서

본 문서는 비즈니스 요구사항과 업무 스펙만 다룹니다.
기술 구현 방식, API, 엔티티, 배포 절차는 별도 문서에서 관리합니다.

---

## 1. 제품 개요

*   CMMS-NODE는 사내 설치형 설비보전관리시스템입니다.
*   인터넷 공개 SaaS를 기본 전제로 하지 않습니다.
*   기본 운영 대상은 소규모 조직이며, 테넌트별 권장 동시사용자는 10명 이내입니다.

---

## 2. 사용자와 권한

### 2.1 사용자 범위

*   회사(테넌트) 단위로 운영합니다.
*   각 회사는 공장(Plant), 부서(Department), 창고(Warehouse)를 가질 수 있습니다.
*   소규모 사업장을 전제로 하며, 업무 담당이 과도하게 세분화되지 않는 운영을 기본 모델로 합니다.

### 2.2 역할

| 역할 | 업무 의미 | `multiPlant` | 기본 범위 | 사업장 선택 |
|------|------|
| `ADMIN` | 회사 운영 관리자 | `Y` | 회사 전체 | 헤더에서 사업장 또는 전체 선택 |
| `MANAGER` | 현장 운영 관리자 | `N` | `lastLoginPlantId` 사업장 | 불가 |
| `USER` | 일반 사용자 | `N` | `lastLoginPlantId` 사업장 | 불가 |
| `PURCHASER` | 구매·재고 담당 | `Y` | 회사 전체 | 헤더에서 사업장 또는 전체 선택 |
| `SYSTEM` | 플랫폼 전역 관리자 | 전역 | 전체 회사/사업장 | SYSTEM 정책에 따름 |

`Role.multiPlant`는 역할의 멀티사업장 가능 여부를 나타내고, `User.lastLoginPlantId`는 단일 플랜트 사용자의 고정 범위와 멀티플랜트 사용자의 기본 선택값으로 사용합니다. 멀티플랜트 사용자가 헤더에서 사업장을 변경하면 API의 `plantId` 범위도 함께 변경해야 하며, 전체를 선택한 경우에만 회사 전체 범위를 허용합니다.

### 2.4 모듈별 데이터 범위

| 모듈/기능 | 범위 | 기준 필드·정책 |
|------|------|------|
| `MDM` 회사·조직·역할·권한 | Company | `companyId`; Plant/Department/Warehouse는 회사 하위 정보 |
| `EQP` 설비 마스터 | Plant | `companyId + plantId` |
| `INV` 자재 마스터 | Company | 공통 자재 정의. 사업장별 재고는 `STK`에서 관리 |
| `STK` 재고 현황·수불·처리 | Plant/Warehouse | `companyId + warehouseId`; 창고의 `plantId`로 사업장 결정 |
| `PM` 예방점검 | Plant | `companyId + plantId` |
| `WO` 작업지시 | Plant | `companyId + plantId` |
| `WP` 작업허가 | Plant | `companyId + plantId` |
| `PUR` 구매요청 | Company + Plant | `purchase_request.companyId + plantId`; 역할별로 허용된 `plantId` 범위에서 조회·처리 |
| `POR` 구매관리 | Company + Plant | 동일 구매요청의 `companyId + plantId`; `PURCHASER` 중심 멀티사업장 관리 |
| `APR` 전자결재 | Company + 원문서 | 결재함은 관련 사용자 기준, 원문서가 있으면 원문서의 plant 범위도 검증 |
| `BRD` 게시판 | Company | 회사 내부 공용 게시판. 작성자/권한으로 수정·삭제 판정 |
| 발전현황 | Company | 현재 보고 데이터는 회사 기준이며 로그인 사용자의 공통 조회 예외 |
| `SYSTEM` 관리 | Global | `companyId='SYSTEM'`, `roleId='SYSTEM'` 사용자만 접근 |

Company 범위는 테넌트 격리(`companyId`)를 항상 적용합니다. `PUR`와 `POR`는 별도 구매 테넌트나 전사 공용 문서가 아니라 `companyId + plantId`를 문서 범위의 기준으로 사용합니다. 멀티플랜트 역할은 허용된 여러 `plantId`를 조회할 수 있을 뿐, `companyId`를 벗어날 수 없습니다.

### 2.5 공통 권한

| 권한 | 의미 |
|------|------|
| `C` | 생성 |
| `R` | 조회 |
| `U` | 수정 |
| `D` | 삭제 |
| `A` | 직접확정/업무 승인 |

### 2.6 모듈별 역할과 권한

| 모듈 | ADMIN | MANAGER | USER | PURCHASER | 비고 |
|------|------|------|------|------|------|
| `MDM` | CRUD | R | R | R | 기준정보 설정 |
| `EQP` | CRUD | CRUD | R | R | 설비 마스터 |
| `INV` | CRUD | CRUD | R | CRUD | 자재 마스터 |
| `STK` | C/R | C/R | R | C/R | 재고처리 |
| `PM` | CRUD+A | CRUD+A | C/R | R | 예방점검 |
| `WO` | CRUD+A | CRUD+A | C/R | R | 작업지시 |
| `WP` | CRUD+A | CRUD+A | C/R | R | 작업허가 |
| `PUR` | CRUD+A | CRUD+A | C/R | CRUD+A | 구매요청 |
| `POR` | R/U | N | N | R/U | 구매관리 |
| `APR` | CRUD | C/R | C/R | C/R | 전자결재 |
| `BRD` | CRUD | C/R | C/R | C/R | 게시판 |
| 발전현황 | 공통조회 | 공통조회 | 공통조회 | 공통조회 | 로그인 사용자 공통 |
| SYSTEM | SYSTEM 전용 | N | N | N | 플랫폼 관리 |

### 2.7 권한 운영 원칙

*   `U/D` 권한은 타인 문서를 포함한 일반 수정/삭제 권한을 의미합니다.
*   임시저장(`T`) 문서는 본인에 한해 일반 `U/D` 권한 없이도 수정/삭제할 수 있습니다.
*   업무문서의 반려(`R`) 건은 삭제하지 않고 수정 후 재상신 대상으로 관리합니다.
*   첨부파일은 독립 권한이 아니라 원문서 권한을 따릅니다.
*   첨부파일은 첨부 그룹 번호 기반으로 접근하므로, 조회 권한은 최소 범위로 운영합니다.
*   발전현황은 문서형 업무가 아니라 로그인 사용자 공통 조회 예외로 운영합니다.
*   `SYSTEM` API는 일반 모듈 권한이 아니라 `SYSTEM` 사용자 여부로만 판정합니다.
*   `STK`는 거래 누적형 구조이므로 일반 수정(`U`)·삭제(`D`) 권한을 기본 사용하지 않습니다. 필요 시 마지막 거래 취소 또는 반대 거래 생성 방식으로 처리합니다.
*   구매요청(`PUR`)은 일반 업무 권한으로 처리하며, 사용자와 관리자는 권한에 따라 자기 사업장 범위에서 사용합니다.
*   구매관리(`POR`)는 `PURCHASER`가 멀티사업장 범위에서 관리합니다. `ADMIN`은 운영 예외 관리자로 `R/U`를 사용할 수 있고, `MANAGER`와 `USER`에는 기본 `POR` 권한을 부여하지 않습니다.

### 2.8 계정과 승인 정책

*   공개 회원가입 사용자는 기본적으로 미승인 상태로 생성합니다.
*   회사 `ADMIN`이 역할 부여와 사용 승인 후 로그인할 수 있습니다.
*   `SYSTEM` 사용자가 신규 회사를 생성할 때 입력한 관리자 계정은 즉시 사용 가능한 초기 `ADMIN`으로 생성합니다.

### 2.9 구매·재고 권한 구분

*   `PUR`: 구매요청 등록, 수정, 상신, 직접확정
*   `POR`: 발주일, 예정도착일, 배송시작일, 종료 처리
*   `STK`: 실제 입고, 출고, 이동, 조정 처리

동일한 구매요청 문서를 기준으로 요청, 구매관리, 입고를 분리합니다.

## 3. 공통 업무 규칙

### 3.1 문서 상태

*   임시저장(`T`)
*   진행중(`P`)
*   완료(`C`)
*   직접확정(`S`)
*   반려(`R`)
*   취소(`X`)
*   구매 처리 종료(`E`)

### 3.2 문서 처리 원칙

*   임시저장 문서는 공식 문서가 아니며 본인이 자유롭게 수정/삭제할 수 있습니다.
*   업무문서의 반려 건은 삭제하지 않고 수정 후 재상신 대상으로 관리합니다.
*   전자결재(`APR`)의 반려 건은 원문 수정 재상신을 하지 않고, 이력 보존을 위해 새 문서로 다시 상신합니다.
*   확정 이후 문서는 삭제보다 상태 이력 유지가 우선입니다.

### 3.3 첨부파일 원칙

*   첨부파일은 독립 권한이 아니라 원문서 권한을 따릅니다.
*   내부 설치형 환경을 전제로 하며, 모듈 조회 권한은 최소 범위로 운영합니다.
*   첨부 그룹 번호 추정만으로 접근 범위가 넓어지지 않도록 `R` 권한을 과도하게 열지 않습니다.

### 3.4 인증과 세션 원칙

*   access token 기본 만료는 30분입니다.
*   refresh token 기본 만료는 3일입니다.
*   화면에 세션 타이머, 수동 연장 버튼, 만료 임박 팝업은 두지 않습니다.
*   refresh 실패 시에만 재로그인 안내를 표시합니다.

### 3.5 조회 범위 원칙

*   기본 조회 범위는 현재 회사입니다. `plantId`를 지정하면 해당 사업장으로 조회하고, 생략하면 회사 전체 사업장을 조회합니다.
*   멀티플랜트 권한자는 헤더에서 특정 사업장 또는 전체를 선택할 수 있습니다. 전체 선택은 `activePlantId`를 비우고 `plantId`를 생략하는 방식으로 처리합니다.
*   `multiPlant=N` 역할은 사업장 선택 대상이 아니므로 `lastLoginPlantId` 사업장으로 제한합니다.
*   생성·수정·삭제·상태변경 등 단일 문서 처리는 문서의 `plantId`를 필수로 검증합니다.
*   결재함은 본인 연관 문서만 조회합니다.
*   발전현황은 활성 플랜트/작성자 기본조건 없이 공통 조회합니다.
*   구매요청은 일반 사용자의 자기 사업장 범위에서 조회합니다. `PURCHASER`와 `ADMIN`은 멀티사업장 범위에서 구매요청을 관리할 수 있습니다.

## 4. 모듈별 기능 스펙

### 4.1 기준정보 관리

*   회사별 공장, 부서, 역할, 사용자, 창고, 공통코드를 관리합니다.
*   운영자가 변경 가능한 분류/선택지는 DB 코드로 관리합니다.
*   상태 전이, 권한 판단, 로직 분기에 직접 쓰는 값은 정책 상수로 관리합니다.

정책 상수 대표 예시:
*   모듈 코드
*   권한 액션
*   결재 단계/행위
*   문서 상태
*   구매 진행상태
*   재고 거래유형/사유

### 4.2 설비/자재 마스터

*   설비 마스터를 관리합니다.
*   자재 마스터와 안전재고를 관리합니다.
*   목록 출력물을 제공합니다.

### 4.3 예방점검/작업지시/작업허가

*   계획과 실적으로 구분합니다.
*   예방점검은 건별 계획과 기간을 정해 주기 작업을 계획할 수 있습니다.
*   계획은 점검유형, 계획기간, 점검항목, 기준값(`min/max/base`)을 관리하며 점검항목 템플릿에서 불러올 수 있습니다.
*   예방점검 실적은 계획 참조 기반이 원칙이며, 운영상 별도 실적 등록도 허용할 수 있습니다.
*   실적이 확정될 때만 설비 점검주기의 최근점검일과 다음점검일을 갱신합니다.
*   작업지시는 계획과 실적이 1:1 관계를 기본으로 합니다.
*   작업지시는 작업내용, 담당자, 소요자재, 공수 및 비용을 기록합니다.
*   작업허가는 계획 문서 중심이며, 현장 완료 확인은 별도 서명/운영 절차를 포함할 수 있습니다.
*   고위험 작업은 LOTO 및 체크시트 확인 후 결재 또는 직접확정합니다.
*   결재와 직접확정 규칙을 공통 적용합니다.
*   목록은 문서번호, 제목, 작성자 기준 검색을 제공합니다.
*   기본 조회조건은 활성 플랜트를 기준으로 하며, 작성자 기본값 제공 여부는 모듈 운영 목적에 따라 다를 수 있습니다.
*   목록 출력과 건별 전표 출력을 제공합니다.
*   상세 화면에서 임시저장, 상신, 직접확정 기능을 제공하며 권한에 따라 버튼 노출을 조정합니다.

### 4.4 구매재고관리

#### 4.4.1 구매요청

*   현업은 구매요청을 등록합니다.
*   요청 시 예정 입고 창고를 지정합니다.
*   일반 사용자의 구매요청은 자기 사업장 내 권한자가 조회할 수 있으며, 본인 문서만 보도록 제한하지 않습니다.
*   `PURCHASER`는 `PUR` 권한이 있는 경우 멀티사업장 구매요청을 관리할 수 있습니다.
*   상세 화면에서 요청 본문 수정, 상신, 직접확정을 처리합니다.
*   요청 본문 편집은 `PUR` 권한 기준으로 판정합니다.

#### 4.4.2 구매관리

*   `PURCHASER`는 동일 요청 문서 기준으로 전 사업장의 발주/배송 상태를 관리합니다.
*   통합발주, 분할발주는 시스템 강제보다 사용자의 별도 발주서/실무 판단을 우선합니다.
*   구매요청 화면과 구매관리 화면은 구분하며, 권한도 `PUR`와 `POR`로 분리합니다. `POR`는 별도 발주 생성 권한이 아니라 기존 요청의 후속 관리 권한입니다.
*   상세 화면은 동일 문서를 조회하지만 요청 본문은 읽기 중심, 발주/배송/종료 정보는 `POR` 권한으로 편집합니다.
*   종료는 자동이 아니라 명시적으로 처리합니다.

#### 4.4.3 입고 처리

*   입고는 요청자 또는 재고/구매 담당자가 처리할 수 있습니다.
*   구매요청 화면이나 구매관리 화면에서 요청번호 기반으로 재고처리 화면에 진입할 수 있습니다.
*   실제 재고 반영 권한은 `STK`를 따릅니다.

### 4.5 재고관리

*   재고는 입고, 출고, 이동, 조정으로 처리합니다.
*   이동은 같은 사업장(플랜트) 내 기준입니다.
*   사업장 간 이동은 별도의 출고-입고 2단계를 거칩니다.
*   구매입고는 구매요청 문서를 참조합니다.
*   목록과 전표(입고증, 출고증, 이동전표 등)를 생성하며, 상세 사유와 참조전표를 표기합니다.
*   조회 화면은 현황, 수불, 이력 중심으로 운영합니다.
*   취소는 마지막 거래인 경우만 허용하고, 그 외에는 반대 거래로 정정합니다.

### 4.6 전자결재

*   결재 문서는 기안-합의/승인-완료 흐름을 따릅니다.
*   결재 상태는 `T` 임시저장, `P` 진행, `C` 완료, `R` 반려를 기본으로 하며 직접확정(`S`)과 취소(`X`)를 별도로 관리합니다.
*   조회는 본인이 연관된 문서만 가능합니다.
*   임시저장 상태의 수정은 자유롭습니다.
*   반려 문서는 수정 재상신하지 않고 새 문서로 다시 상신합니다.
*   연계 문서 상태는 결재 결과에 따라 전이됩니다.
*   결재 상신 시 연계 업무문서는 `P`, 승인 완료 시 `C`, 반려 시 `R`로 전이하며 하나의 업무 트랜잭션으로 처리합니다.

### 4.7 게시판

*   사내 공지와 일반 게시글, 댓글을 관리합니다.
*   작성자 본인 글과 댓글은 자유롭게 수정/삭제할 수 있습니다.
*   타인 글과 댓글 수정/삭제는 일반 게시판 권한을 따릅니다.

### 4.8 발전현황

*   발전현황은 문서형 업무가 아니라 보고 기능입니다.
*   활성 플랜트/작성자 기본조건을 두지 않습니다.
*   인증된 사용자라면 모두 조회할 수 있습니다.

### 4.9 SYSTEM 관리

*   `SYSTEM` 사용자는 회사 생성, 사용자 활성화, 로그인 이력 조회 같은 플랫폼 관리 기능을 수행합니다.
*   일반 회사의 `ADMIN`은 이 영역에 접근할 수 없습니다.

## 5. 화면 운영 원칙

*   메뉴는 업무 목적 단위로 구성합니다.
*   동일 문서를 조회하더라도 권한에 따라 읽기 전용/편집 가능 범위가 달라질 수 있습니다.
*   문서번호 클릭은 출력 진입으로 사용하는 패턴을 우선합니다.
*   입고는 별도 구매입고 메뉴보다 구매화면 또는 재고처리 화면 진입을 기본으로 합니다.
